# QA 测试知识库工作流

把一条需求从原始文档推进到可执行、可追溯的测试资产，并保持知识库结构统一。核心不是"多写"，而是**门禁、出处、不弱化断言**。

## 0. 先定位工作区

1. 当前目录或其上级存在 `RELEASE-*` 目录时，即视为 vault 根目录。
2. 找不到时询问用户 vault 路径；不要凭空猜测或新建一堆空目录。
3. 先读目标需求的 `需求.md`（frontmatter、确认结果）和同目录已有文件，再决定下一步。
4. 原始输入（docx、原型、历史 xmind）默认在 `_收件箱/`；已归档输入在需求目录 `附件/`。

## 1. 目录与命名（固定）

```
{vault}/
├── _模板/  _工具脚本/  _附件/  _收件箱/  _归档/  _审核临时/
└── RELEASE-{版本}/
    └── {序号}.{需求名}/
        ├── 需求.md
        ├── 测试点.md
        ├── 测试用例.md
        ├── 冒烟测试用例.md
        ├── 测试点审核报告.md              # 按需
        ├── 执行记录-{端}-{YYYYMMDD}.md    # 按需
        └── 附件/
```

- 文件名固定，便于脚本扫描与全文检索；不要用"需求V2""用例-最终"之类命名。
- 需求目录 `{序号}.{需求名}`，序号在同一 release 内递增。
- 用例编号 `TC-{NN}`；冒烟编号 `TC-S-{NN}`，历史文件可能为 `SMT-{NNN}`，同一需求内沿用既有体系，不混用。
- 每个 md 必须有 frontmatter。`type` 以 vault 内既有取值为准；新库用 `requirements` / `test-points` / `test-cases` / `smoke-test-cases` / `review-report` / `execution-record`。

详细规范见 `references/vault-conventions.md`。

## 2. 工作流与门禁（核心）

```
需求输入 → ① 需求梳理 → ② 用户确认 A/B/C → ③ 测试点 → ④ 测试用例 → ⑤ 冒烟用例 → ⑥ xmind
```

| 步骤 | 触发条件 | 产出 | 完成后 |
|---|---|---|---|
| ① 需求梳理 | 需求输入到位 | `需求.md` + 确认点清单 | 停下，交用户确认 |
| ② 确认 | 用户回复确认结果 | 回填 `需求.md` | 继续 |
| ③ 测试点 | A/B/C 类已确认 | `测试点.md` | **停下汇报** |
| ④ 测试用例 | 用户明确说"生成测试用例" | `测试用例.md` | 停下 |
| ⑤ 冒烟用例 | 用户明确说"生成冒烟用例" | `冒烟测试用例.md` | 停下 |
| ⑥ xmind | 用户明确说"转 xmind" | 同名 `.xmind` | 停下 |

**门禁判定**：只有用户在当前轮次明确发出下一步指令才算放行。"好的/继续/收到"不等于授权生成下一份文件；不确定就问一句。绝不把 ③④⑤⑥ 合并执行。

## 3. 需求梳理

输入包括 PRD（docx / PDF / 链接）、原型（含批注）、流程图、设计稿、历史 xmind。

`需求.md` 固定顺序：需求输入 → 范围（含**明确不做**）→ 业务目标 → 功能清单（编号 / 模块 / 优先级 / PRD 章节）→ PRD 与原型差异 → 关键业务规则 → 确认点清单 → 相关资料。

确认点分四类，每条必须给出**建议默认方案**，让用户能一次回复"全部按默认"：

- **A 阻塞性矛盾**：PRD 内部、或 PRD 与原型冲突，必须先定
- **B 规则缺失**：影响用例设计，需要补充定义
- **C 待补充占位**：PRD 标注 [待补充] 的项
- **D 风险提示**：不阻塞，但需知会相关方（合规、依赖、数据迁移等）

确认结果回填 `需求.md`：写明日期与确认方式（逐条 / 全部按建议默认 / 例外项）；之后测试点与用例一律以回填结果为准。详见 `references/requirements.md`。

## 4. 测试点（质量核心）

前提：`需求.md` 中 A/B/C 类已确认。未确认时不要写测试点，回到需求梳理。

硬约束：

1. **四层结构**：中心主题 → 端 → `N、模块` → `N.M 分类` → 测试点，禁止第五层分组节点。
2. **每条有出处**：`（PRD §x.x / AC-xx / 批注n / 原型页 / 确认Ax）`；禁止"（PRD）""（待补充）"这种无定位出处。
3. **编号** `TP-{端代号}{模块号两位}-{序号两位}`；端代号一份需求内定义一次（A=主端、B=小程序/接收端、C=后台、D=非功能）。
4. **可独立断言就独立编号**；子节点只用于分支细化、待确认问题、嵌套场景说明。
5. **写具体阈值**：50+、23h59m、9 张、±15 天；不写"极多/较大/较长"。
6. **负向断言显式化**：无入口、不可编辑、只读、无操作入口、不展示，必须写出来。
7. **不臆造、不静默采纳**：实现与 PRD 冲突时写"以实际实现取证，与 PRD 口径存疑待对齐"；开发口头口径不能直接覆盖已确认口径。

覆盖维度表、前置数据要求、LLM 专项、自检清单、禁止行为见 `references/test-points.md`，写之前必读。

汇报格式：`测试点.md 已生成：N 模块 / M 分类 / K 条；待确认 X 条；与现有用例差异 Y 处（编号）。等候指令。`

## 5. 测试用例

仅在用户明确指令后生成。表格列固定：`编号 | 前置条件 | 操作步骤 | 预期结果 | 优先级 | 关联 | 执行结果`。

- 步骤和预期一一对应、可执行；前置写清账号 / 角色 / 数据。
- "关联"填 TP 编号、PRD 章节或 AC，保证可追溯。
- 优先级：P0 主流程与高风险，P1 重要异常与辅助功能，P2 兼容与非功能。
- 每个 P0 模块至少有正向、异常、边界；高风险模块加深，不做平均铺量。
- 变更驱动：只覆盖新需求 + 受影响模块，存量靠主流程回归兜底。
- 修订测试点后，必须在汇报中列出受影响的 TC 编号。

详见 `references/test-cases-and-smoke.md`。

## 6. 冒烟测试用例

仅在用户明确指令后生成。它不是全量用例的子集，而是独立的端到端主流程文件：

- 用最少用例覆盖全部正向 P0 主链路；不覆盖单字段、弱网、兼容性。
- 每条是多步操作 + 多步预期的完整流程。
- 涉及多端时按"归属方 → 接收方 → 数据回写"或"发起端 → 消费端 → 反向确认"组织成一条。
- 默认 P0；编号在同一文件内递增；每条关联 TP 或 PRD 章节。
- 写明公共前置数据与准出标准（全通过才可提测/上线，失败重跑关联链路）。

## 7. xmind 导出

仅在用户明确指令后执行：

```bash
python scripts/md2xmind.py "RELEASE-x/n.需求/测试点.md"
```

输出与源文件同目录、同名 `.xmind`。生成后核对一级分支数与条目数是否和 md 一致。**不要**在生成测试点后自动转 xmind。

## 8. 审核与答疑

- **审核已有测试点/用例**（手工改过 xmind、生成用例前、需求变更后）：全量节点逐项对输入核对，并做 xmind 与 md 的脚本化 diff。问题按 A 口径错误 / B 新待确认 / C 覆盖缺口 / D 断言弱化 / E 共有遗漏 / F 结构 / G 合理增强 分类，每条给"现文 / 基线或依据 / 问题 / 依据 / 建议"。报告写入 `测试点审核报告.md`。**禁止**以"精简"为名删除、合并或弱化断言。
- **需求口径答疑**：先给结论 → 列出处（PRD § / AC / 批注号 / 确认点）→ 主动提示易混口径。同名概念在不同模块规则不同时，用表格显式对比。
- **执行记录**：按 `执行记录-{端}-{YYYYMMDD}.md` 记录环境、设备、执行方式、范围、证据截图目录；结果用 通过 / 失败 / 部分通过 / 阻塞 / 未执行，并写实际观察。

详见 `references/review-and-answers.md`。

## 9. 汇报习惯

- 结论先行，给数字：模块数、条目数、待确认数、差异数。
- 改动要能定位：编号列表 + 受影响文件。
- 每次停在门禁处，明确说"等候指令：生成用例 / 生成冒烟 / 转 xmind"。
- 中间过程（diff、抓包、批量校验）写文件放 `_审核临时/`，对话只贴结论与关键报错。
