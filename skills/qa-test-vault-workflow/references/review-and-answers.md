# 审核、答疑与执行记录

## 一、测试点 / 用例审核

### 1. 触发场景

- 测试点被手工改过 xmind，md 未同步
- 生成测试用例之前，确认测试点基线可靠
- 需求变更、确认点回填之后
- 用户直接说"审核一下测试点/用例"

### 2. 审核方法

1. **全量核对**：xmind 或 md 的全部节点，逐项对 PRD、原型、流程图、确认结果核对，不能抽样。
2. **脚本化 diff**：xmind 解压 `content.json` 抽标题，与 md 抽条目比对，输出新增 / 删除 / 文字改动三张清单，放 `_审核临时/{需求名}/`。
3. **反向核对前置数据**：账号、样本、时间边界能否支撑每条断言。
4. **联动检查**：测试点改动是否波及 `测试用例.md`，列出失效 TC。

### 3. 问题分类

| 类别 | 含义 | 处理 |
|---|---|---|
| A 口径错误 | 与 PRD / 已确认口径直接冲突 | 必须修正后才能进用例 |
| B 新待确认 | 审核中发现的规则缺失 | 并入 `需求.md` 确认点 |
| C 覆盖缺口 | 删除、遗漏导致覆盖不足 | 建议恢复或补充 |
| D 断言弱化 | 阈值、负向断言、范围被改弱 | 恢复基线表述 |
| E 共有遗漏 | 基线与现文都没覆盖 | 建议补充 |
| F 结构问题 | 层级、编号、出处格式 | 整理 |
| G 合理增强 | 比基线更准确的改动 | 保留，记录原因 |

### 4. 每条问题的写法

```markdown
### A-1 TP-xxx：一句话结论 ⛔

- **现文**：…
- **基线/依据**：…
- **问题**：说明它错在哪、会导致什么后果。
- **依据**：
  1. PRD §x.x：原文摘录。
  2. 流程图 x-y：…
  3. 确认点 A3：…
- **建议**：恢复/改为……；若来自开发口头口径，先走产品确认。
```

只写"建议优化"不算审核结论；必须给出可执行改法。

### 5. 报告结构

```
frontmatter（type: review-report, date）
# 测试点审核报告——{需求名}
> 审核对象（文件 + 时间 + 条目数）
> 审核依据（输入物 + 确认结果 + 基线）
> 审核方法
## 0. 总体结论（覆盖框架 + 主要问题 + 汇总表）
## A. 口径错误
## B. 新待确认
## C. 覆盖缺口
## D. 断言弱化
## E. 共有遗漏
## F. 结构问题
## G. 合理增强
```

总体结论先给判断：能不能进用例；不能则说明卡在哪几类。

### 6. 红线

- 不以"精简""去重"为名删除、合并、弱化测试点。
- 不用开发口头口径覆盖 PRD 或已确认口径。
- 发现删除时，先恢复并给依据，再讨论是否真的多余。
- 审核报告只增不改历史结论；修订后追加复审记录与日期。

## 二、需求口径答疑

用户常拿功能俗称直接问，不给文件路径。回答结构固定：

1. **结论**：一句话回答"是/不是/分情况"。
2. **出处**：PRD §、AC 编号、批注号、确认点编号，便于跳转核对。
3. **易混点**：主动指出同名概念在其他模块的不同规则，或"默认展示 N 个 + 展开"与"最多选 N 个"这类形似口径。

并列信息用表格，例如：

| 场景 | 规则 | 出处 |
|---|---|---|
| 发帖选标签 | 最多 3 个 | PRD §6.2 |
| 举报分类展示 | 默认 3 个 + 展开 | PRD §7.1 |

检索顺序：先定位需求目录 → 再全文检索关键词 → 读附件 PRD 原文确认 → 最后回答。不要在未定位文件时凭记忆作答。

## 三、执行记录

### 1. 文件与 frontmatter

`执行记录-{端}-{YYYYMMDD}.md`，`type: execution-record`，`exec-date` 写执行日期。

### 2. 必写内容

- 执行日期与时间段
- 设备 / 系统 / 分辨率 / 序列号（真机或模拟器）
- 应用包名、账号、角色
- 执行方式（手工 / adb / 自动化脚本）与坐标基准
- 执行范围与明确未覆盖项
- 证据截图目录与清单

### 3. 结果表

| 编号 | 结果 | 实际观察 / 说明 |
|---|---|---|
| TC-001 | 失败 | 页面显示 A，预期 B（见截图 tc001_after.png） |

- 结果只用：通过 / 失败 / 部分通过 / 阻塞 / 未执行。
- "实际观察"写看到的现象，不写推测原因；能引用截图就标文件名。
- 阻塞要写清缺什么（入口、账号、数据、环境），便于后续补测。
- 失败项在记录末尾汇总，并注明是否已提单。

## 四、中间产物

diff、抽取文本、批量校验结果、抓包记录都写文件放 `_审核临时/{需求名}/`，对话里只贴结论、关键数字和报错。避免把大段节点树或日志刷进对话。
