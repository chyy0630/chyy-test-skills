# 知识库结构约定

## 1. 目录职责

| 目录 | 用途 | 维护规则 |
|---|---|---|
| `_模板/` | 需求、测试点、用例、冒烟、审核、执行记录模板 | 新需求从这里复制，不直接改模板做需求 |
| `_工具脚本/` | 跨迭代复用的脚本（md→xmind、统计、索引） | 一次性脚本也可先放这里，稳定后再沉淀 |
| `_附件/` | 全局截图、流程图 | 跨需求复用的资料才放这里 |
| `_收件箱/` | 原始输入暂存：docx、原型、待导入 xmind | 消化后移入对应需求 `附件/`，保持收件箱接近空 |
| `_归档/` | 已结束迭代或重构前备份 | 保留原文件与 release 信息，不二次编辑 |
| `_审核临时/` | diff 输出、抽取文本、审核中间产物 | 可清理，不作为正式交付物 |
| `RELEASE-{版本}/` | 一次迭代的全部需求 | 迭代结束后整体移入 `_归档/` |

需求目录内固定文件：

```
需求.md 测试点.md 测试用例.md 冒烟测试用例.md
测试点审核报告.md 执行记录-{端}-{YYYYMMDD}.md
附件/
```

## 2. 命名规则

| 对象 | 规则 | 示例 |
|---|---|---|
| release | `RELEASE-{版本号}` | `RELEASE-24` |
| 需求目录 | `{序号}.{需求名}`，序号迭代内递增 | `1.社区`、`2.用户消息` |
| 需求文件 | 固定文件名 | `需求.md` / `测试点.md` / `测试用例.md` |
| 用例编号 | `TC-{两位序号}`，同文件内递增 | `TC-01` |
| 测试点编号 | `TP-{端代号}{模块号两位}-{序号两位}` | `TP-A01-03` |
| 冒烟编号 | `TC-S-{两位序号}`；历史文件可为 `SMT-{三位序号}` | `TC-S-01` / `SMT-001` |
| 审核报告 | `测试点审核报告.md` | 一场审核一份，修订时更新而非新建 |
| 执行记录 | `执行记录-{端}-{YYYYMMDD}.md` | `执行记录-Pad端-20261126.md` |

## 3. Frontmatter

所有正式 md 必带：`release`、`req-id`、`module`、`type`、`tags`。按类型追加：

| type | 追加字段 |
|---|---|
| `requirements` | `jira`、`status`、`prd_version`、`prd_date`、`原型地址` |
| `test-points` | 无 |
| `test-cases` | 无 |
| `smoke-test-cases` | 无 |
| `review-report` | `date` |
| `execution-record` | `exec-date` |

`type` 取值以目标 vault 既有为准。旧库常见中文值（`需求` / `测试点` / `测试用例` / `冒烟测试用例`）与新库英文值是同一含义，**不要在新文件里混用两套**。

```yaml
---
release: RELEASE-x
req-id: AI-XKZS-01
module: 模块名
type: requirements
jira: PROJ-0000
status: 草稿
prd_version: v2.0
prd_date: 2026-11-05
tags: [RELEASE-x, 模块名]
---
```

`tags` 至少包含 release 与模块名；需要区分端 / 期次时追加（如 `一期`、`Pad端`）。`req-id` 与目录序号不一致时（如用 `AI-XKZS-01` 这种业务编号），在需求.md 中说明映射。

## 4. 附件规则

- **PRD 原件与全文 md 都放 `附件/`**。docx 不可全文检索，必须转 md，保留章节号、AC 编号、批注号。
- 原型：保存 `*.html` + `*janus.data.json`（如工具导出），并把可见文案抽成 `*_文本抽取.md`，便于检索与引用。
- 只有原型没有 PRD 时，把批注全文录入 `需求.md` 或附件文本，批注即口径，引用时写"批注n（作者）"。
- 执行截图放 `附件/执行截图-YYYYMMDD/`，命名 `{用例编号}_{动作}.png`，便于执行记录逐条引用。
- 附件不重复存：同一文件在需求目录与全局 `_附件/` 只保留一份，另一处用链接。

## 5. xmind 约定

- 正式产物统一由 `scripts/md2xmind.py` 从 md 生成，**md 是唯一事实源**。手工改 xmind 后必须回写 md，并做一次 diff，否则下次生成会覆盖手工修改。
- 同一需求目录只保留一个测试点 xmind：优先 `测试点.xmind`；历史命名 `{需求名}_测试点.xmind` 可保留，但不要两份并存。
- 历史 xmind 导入：xmind 本质是 zip，解压后 `content.json` 是树结构。先放到 `_收件箱/`，再写一次性转换脚本放 `_工具脚本/`，转出 md 后归位到需求目录并补 frontmatter。

## 6. 结果枚举

用例与执行记录统一使用：`通过` / `失败` / `部分通过` / `阻塞` / `未执行` / `不适用`。不要自造"OK""pass""待定"等值。

## 7. 全库一致性规则

- 同一需求内不混用编号体系（TC-S 与 SMT 二选一）。
- 不新建"最终版""新版"文件，修订直接改原文件；需要留底时整体备份进 `_归档/` 并带日期。
- 删除测试点保留断号，不重排，便于 diff 与追溯。
- 测试点、用例、xmind 三者的编号与条目应能互相对上；对不上就是审核项。
