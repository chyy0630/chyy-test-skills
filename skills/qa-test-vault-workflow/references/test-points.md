# 测试点编写标准

## 0. 调用前提（缺一不可，缺则停下问用户）

- 已存在 `需求.md`，且 A/B/C 类确认点在确认结果中已逐条落定（含"全部按建议默认"）。
- 已列清输入物：PRD / 原型（含批注）/ 流程图 / 设计稿 / 后端设计 / 格式表，每项都有可引用的编号。
- 只有原型无 PRD 时，原型批注全文已录入 `需求.md`，批注即口径。
- 端的叫法已确认：业务方叫"设备端"就写设备端，不要自造"Pad 端"。

未满足时不要写测试点，先回到需求梳理。

## 1. 文件骨架（顺序固定）

```
frontmatter（release / req-id / module / type / tags）
# 测试点——{需求名}
> 依据：列出全部输入物 + 版本 + 确认日期
> 出处简写：列出本文件用到的全部出处代号
> 编号规则：TP-{端代号}{模块号}-{序号}
## 测试主体与前置数据
## {端 1，如 App 端}
### 1、{模块名}
#### 1.1 {分类名}
- [ ] TP-A01-01 ……（出处）
## {端 2}
## 【后台】{端 3}
## 跨端与接口
## 非功能与其他
```

- 端命名跟随业务叫法；后台模块统一加 `【后台】` 前缀。
- 模块号整份文件连续递增，不按端重置（如设备端 1–7、小程序端 8–10、后台 11、非功能 12–14）。

## 2. 四层结构（硬约束）

中心主题 → 端 → `N、模块` → `N.M 分类` → 测试点。**不允许第五层分组节点。**

案例：某次 review 在 `9.1` 下又加"首页 / 报告查询"分组，直接造成层级失控。需要再细分时，拆成 `9.1` / `9.2` 两个分类，或在分类下直接挂测试点。

常用分类（按需取用，不要求凑齐）：页面 UI 展示、基础操作、页面跳转、网络异常、边界与极端场景、数据联动、状态与权限、兼容、边界值与校验。允许模块内定制（如"报告可识别标准"）。

## 3. 编号规则

格式：`TP-{端代号}{模块号两位}-{序号两位}`。

- 端代号：A = 主端（App / 设备端）、B = 小程序 / 接收端、C = 后台 / 接口、D = 非功能。一份需求定义一次，写在文件抬头。
- 序号在模块内连续递增；删除条目不重排，保留断号。
- 子节点中**可独立断言的必须独立编号**；只有纯备注、嵌套场景说明、待确认问题才允许不编号。某次 review 出现 9 处未编号子节点，其中 6 处应赋编号——生成时自查。

## 4. 出处标注（每条必填）

格式：`（出处1 / 出处2）` 写在条目末尾。抬头声明允许的代号：

| 代号 | 含义 |
|---|---|
| `PRD §x.x` | PRD 章节 |
| `AC-xx` / `EX-xx` | 验收标准 / 异常用例编号 |
| `批注n` | 原型批注序号（可带作者） |
| `ui_n` / `p1`~`pN` / `t1`~`tN` | 设计稿屏 / 主端原型页 / 小程序原型页 |
| `流程x-y` | 流程图节点 |
| `场景A`~`F` | 业务场景编号 |
| `规则n` | 需求.md 中的业务规则编号 |
| `接口` / `格式表` | 后端设计文档 / 数据格式表 |
| `确认Ax/Bx/Cx` | 已确认的确认点编号 |

禁止"（PRD）""（待补充）""（需求文档）"这类无定位出处。

## 5. 必须覆盖的维度

每个核心模块按下表自检；不适用写"N/A 因为 …"，不能直接跳过。

| 维度 | 要点 |
|---|---|
| 正向主链路 | UI 字段齐全、基础操作、页面跳转 |
| 负向断言 | "无 XXX 入口""不可编辑""不显示关系称谓"；只读区块写"只读、无操作入口" |
| 边界值 | 写具体阈值：50+、23h59m、9 张、±15 天；不写"极多/较大" |
| 网络异常 | 加载失败、超时、断网、弱网、重试幂等 |
| 状态机 / 竞态 | 确认瞬间取消、并发刷新、未刷新时数据变更 |
| 数据联动 | 跨页/跨端按钮状态、计数、列表刷新时机 |
| 接口越权 | 直调未授权 ID 返回 403 / 业务错误码；查询层切断，不能只靠前端隐藏 |
| 多端一致 | 文案、按钮、空态在两端/三端一致；不要只查一端。某次 review 把"全端检索"改成"小程序检索"，放过了矛盾源头 |
| 兼容 | 系统版本、机型、深色模式、大字体（端内支持时） |
| 回归面 | 本期改动模块的相邻功能、被复用链路（如新增模型不影响旧模型调用） |
| 缓存与下次请求 | 删除/解绑后，已打开页面与下次请求的差异口径要分别写 |

## 6. 测试主体与前置数据（必写）

这不是装饰章节，是用例能否落地的依据。至少列出：

- **账号矩阵**：归属方 / 查看方 / 第二查看方 / 管理员；每个账号下的角色与数据。
- **样张/数据集**：涉及识别或解读时，列清类型（清晰/模糊/反光/非目标/字段缺失/异常值）。
- **时间可造场景**：过期边界（23h59m / 24h）、间隔边界（14/15/16 天）、链式日期。
- **格式与分辨率**：HEIC、TIFF、WEBP、BMP、JPG、PNG；4K/8K 边界。
- **越权数据**：他人 ID、已删除 ID、过期凭证。

前置数据必须与测试点反向核对：每条断言都能在数据里找到支撑。某次 review 删掉了第二个账号和正式成员，导致 3 条测试点无法执行——这是审核必查项。

## 7. 子节点的合法用法

仅三种：

1. **细化分支**：父条目是入口，子条目是不同输入下的预期（"有数据 / 无数据"走同一按钮）。
2. **待确认问题**：写"（待与产品/开发确认）"，不静默采纳某一种口径。
3. **嵌套场景说明**：多步前置的补充描述。

不允许把独立断言塞进子节点逃避编号，也不允许用子节点替代分类层级。

## 8. LLM / 算法输出专项

凡涉及 AI 生成、识别、解读，必须写：

- **结构验收**：输出段落数、字段顺序、是否合并、分段是否符合口径。
- **关键词级验收**：必须出现 / 不允许出现的措辞（如"可能提示 / 需考虑 / 不排除"）。
- **降级形态**：单份输入、互不相关、只命中一侧时的展示口径。
- **不臆造**：只基于实际提取到的字段，不补未提取指标。
- **口径冲突**：实现与 PRD 不一致时写"以实际实现取证，与 PRD 口径存疑待对齐"，不私自采纳其中一种。
- **模型/版本变更**：同一输入在不同模型版本下的稳定性、回退策略。

## 9. 禁止行为（实际踩过的坑）

- ❌ 擅自合并或删除测试点；删除必须给依据并经用户确认。
- ❌ 弱化断言：把"无勾选清单、无多选"改成"内容同原页面"，把"50+"删掉，把"全端"改"小程序"——具体阈值和负向断言正是测试点的价值。
- ❌ 用开发口头口径直接覆盖 PRD / 已确认口径。正确路径：产品确认 → 改 `需求.md` → 改测试点 → 列受影响用例。
- ❌ 改了测试点不联动用例。每条 A 类口径错误都会让对应 TC 失效，汇报时必须点出受影响 TC 编号。
- ❌ 自动转 xmind。测试点完成即停，等用户单独指令。
- ❌ 把"待确认"写成默认实现，导致后续用例建立在猜测上。

## 10. 完成自检清单

- [ ] frontmatter 字段齐全，tags 含 release 与模块名
- [ ] 抬头三行齐全（依据 / 出处简写 / 编号规则）
- [ ] 编号无重复、无未说明跳号
- [ ] 每条测试点都有可定位出处
- [ ] 四层结构，无第五层分组
- [ ] 可独立断言的子节点已赋编号
- [ ] §5 维度表逐项自检，N/A 写了原因
- [ ] 前置数据与测试点反向核对通过
- [ ] 待确认项已标注，未静默采纳
- [ ] 修订场景：与现有 `测试用例.md` 的差异已列出

## 11. 门禁与汇报

测试点.md 完成 → 停 → 等"生成测试用例" → 用例完成 → 停 → 等"生成冒烟用例" → 冒烟完成 → 停 → 等"转 xmind"。三道门禁独立触发，绝不合并。

汇报：

```
测试点.md 已生成：N 模块 / M 分类 / K 条。
待确认项 X 条（编号）。
与现有测试用例差异 Y 处（TC 编号）。
等候指令：生成测试用例 / 生成冒烟 / 转 xmind。
```
