# 需求梳理与确认

## 1. 输入盘点

先列一张输入表，缺什么、版本、日期都要写清：

| 输入 | 处理 |
|---|---|
| PRD docx / PDF | 转 md 存 `附件/`，保留章节号、AC 编号、批注号 |
| PRD 在线文档 | 导出或逐节摘录，标注版本与导出日期 |
| 原型（墨刀/Figma/HTML） | 另存 html 与数据文件；把可见文案抽成 `_文本抽取.md` |
| 原型批注 | 批注即口径；逐条录入，记 `批注n（作者）` |
| 流程图 | 节点编号化（流程1-1、流程2-3），供测试点引用 |
| 设计稿 | 按屏编号（ui_1…），供 UI 断言引用 |
| 后端设计 / 接口文档 | 关注字段、状态机、权限、错误码 |
| 历史 xmind / 用例 | 先转 md 再对比，不直接在 xmind 上增量改 |

**只有原型没有 PRD** 时，需求.md 必须包含：原型批注全文、页面清单、可见规则推演，并明确"以批注为准"的条目。推演出的规则标为 B 类确认点，不要当成已确认口径。

## 2. 需求.md 结构

1. **需求输入**：表格列输入项、位置、说明（版本 / 日期 / 范围）。
2. **范围总结**：本期做什么、按端拆分；单列"明确不做"，防止测试范围蔓延。
3. **业务目标**：1–3 条，能对应到验收。
4. **功能清单**：`编号 | 模块 | 优先级 | 一句话说明`，编号用 A1/A2、B1/B2 按端分组，并标 PRD 章节。
5. **PRD 与原型差异**：`差异点 | PRD 口径 | 原型呈现 | 当前影响`；有冲突的转入 A 类确认点。
6. **关键业务规则速查**：编号化（R1、R2…），供测试点"规则n"引用。
7. **确认点清单**：A/B/C/D 四张表。
8. **相关资料**：原件、原型地址、文本抽取、流程图。

## 3. 确认点写法

每条一行，列固定：`# | 确认点 | 出处 | 建议默认方案 | 确认结果`。

- **一条只问一件事**。把"角色权限+文案+超时"塞成一条，用户无法逐项确认。
- **出处必须可定位**：PRD §x.x、原型 pN、批注n、流程图 x-y；不写"文档里提到"。
- **建议默认方案必须具体**：给数值、状态、展示与否、失败提示，写成可直接落用例的句子。禁止"按 PRD""按设计""视情况"。
- A 类要写清冲突双方与影响；D 类只写提示与可能影响，不要求确认。

四类边界：

| 类别 | 判定 | 处理 |
|---|---|---|
| A 阻塞性矛盾 | 两处规则互斥，按任一实现都会导致返工 | 必须先定，未定不写测试点 |
| B 规则缺失 | 主流程能走，但异常/边界无定义 | 给建议默认，确认后落测试点 |
| C 待补充占位 | PRD 明写 [待补充]、TBD、占位文案 | 给建议默认；验收以可配置为准 |
| D 风险提示 | 合规、依赖、性能、迁移风险 | 知会，不阻塞 |

## 4. 确认结果回填

- **逐条确认**：填"确认结果"列，写结论而不是"已确认"。
- **一次性确认**：在表上方加引用行，写日期、确认人、覆盖范围与例外，例如：

  > 确认记录（2026-11-25）：A1–A6、B1–B13、C1–C5 全部按"建议默认方案"确认；D 类为风险提示不需确认。确认结果即各表"建议默认方案"列，不再逐行回填。

- **部分确认**：已确认的逐行回填；未确认的保持空白，并在汇报中列出。
- **后续变更**：任何口径变更先回填 `需求.md`，再改测试点，再列受影响的 TC 编号。开发口头口径、群聊结论都不算确认，必须走产品或需求方。

## 5. 汇报格式

```
需求.md 已生成：N 个功能模块（A 端 x 个 / B 端 y 个）。
确认点：A a 条 / B b 条 / C c 条 / D d 条。
A 类摘要：A1 …；A2 …。
范围排除：…
等候确认结果后生成测试点。
```

A 类必须逐条摘要，不要只给数量。
